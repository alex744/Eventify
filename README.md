# Eventify

**API для управления событиями (CRUD операции) и бронированиями.**

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/ru-ru/download/dotnet/10.0)
- [PostgreSQL](https://www.postgresql.org/download/) (версия 16 или выше)
- [Docker](https://www.docker.com/)

## Структура проекта

Проект построен на основе **многослойной архитектуры (Clean/Layered Architecture)**, что обеспечивает разделение ответственности и облегчает тестирование.

### Архитектурные слои

- **WebApi** — внешний уровень, обрабатывающий HTTP-запросы и отвечающий клиенту (включает контроллеры, модели представлений, модули Swagger).
- **Application** — уровень бизнес-логики, обрабатывающий запросы от WebApi и взаимодействующий с уровнем инфраструктуры (включает сервисы, интерфейсы репозиториев, модели запросов/ответов).
- **Infrastructure** — уровень, отвечающий за взаимодействие с внешними системами (например, БД, файловая система), реализация интерфейсов из уровня Application (включает контекст базы данных, реализации репозиториев, миграции EF Core).
- **Domain** — уровень, содержащий доменные модели и бизнес-правила, не зависящие от деталей реализации (включает сущности, перечисления, доменные исключения).

**Правило:** Верхние слои зависят от нижних, но не наоборот.
- `Presentation` зависит от `Application` и `Domain`
- `Application` зависит от `Domain`
- `Infrastructure` зависит от `Domain`
- `Domain` не зависит ни от чего

---

## Описание каждого слоя

#### 1. **Presentation Layer** (`Ya.Events.WebApi`)
**Назначение:** Слой взаимодействия с клиентом. Обработка HTTP-запросов и ответов.

**Содержит:**
- `Controllers/` — REST API контроллеры (`EventsController`, `BookingsController`)
  - Валидация входных данных
  - Обработка HTTP-методов (GET, POST, PUT, DELETE)
  - Возврат стандартизованных ответов с правильными статус-кодами
- `Middleware/` — промежуточные компоненты конвейера запросов
  - `GlobalExceptionHandlingMiddleware` — глобальная обработка исключений
- `Program.cs` — конфигурация приложения и DI контейнер
- `appsettings.json` — конфигурация для среды выполнения

**Ответственность:** Только за приём/отправку данных, валидацию и маршрутизацию.

---

#### 2. **Application Layer** (`Ya.Events.Application`)
**Назначение:** Слой бизнес-логики и оркестрации процессов. Реализует основные сценарии использования (use cases).

**Содержит:**
- `Services/` — сервисы бизнес-логики
  - `EventService` — управление событиями (CRUD)
  - `BookingService` — управление бронированиями, включая синхронизацию  
- `DTOs/` — Data Transfer Objects для передачи данных
  - `Bookings/` — объекты для бронирований
  - `Events/` — объекты для событий
  - `PaginatedResult` — результат с пагинацией
- Реализация правил валидации и бизнес-правил
- Управление транзакциями и координацией между репозиториями
- Использование примитивов синхронизации (`SemaphoreSlim`) для предотвращения race conditions

**Ответственность:** Бизнес-логика, оркестрация работы с данными, обработка доменных событий.

---

#### 3. **Domain Layer** (`Ya.Events.Domain`)
**Назначение:** Ядро приложения. Содержит доменные модели и бизнес-правила, не зависящие от деталей реализации.

**Содержит:**
- `Entities/` — доменные сущности (модели данных)
  - `Event` — событие с валидацией
  - `Booking` — бронирование с управлением статусом
- `ValueObjects/` — перечисления (`BookingStatus`)
- `Exceptions/` — доменные исключения
  - `BookingNotPendingException` — попытка подтвердить несуществующую или уже обработанную бронь
  - `NoAvailableSeatsException` — нет свободных мест
  - `NotFoundException` — событие не найдено
- Валидация на уровне доменной логики

**Ответственность:** Определение сущностей и их правил, не зависит от инфраструктуры.

---

#### 4. **Infrastructure Layer** (`Ya.Events.Infrastructure`)
**Назначение:** Реализация механизмов доступа к данным, работа с внешними сервисами.

**Содержит:**
- `Persistence/` — контекст БД и конфигурация
  - `AppDbContext` — Entity Framework Core контекст
  - `Configurations/` — Конфигурации сущностей (Fluent API)
- `Repositories/` — реализация паттерна Repository
  - `EventRepository` — операции с событиями в БД
  - `BookingRepository` — операции с бронированиями в БД
- `Migrations/` — EF Core миграции для управления схемой БД
- `Services` — реализация фоновых сервисов
  - `BookingProcessingService` — фоновая обработка бронирований  
- `DependencyInjection.cs` — регистрация сервисов инфраструктуры в DI контейнере

**Ответственность:** Работа с базой данных, реализация интерфейсов репозиториев, миграции.

### Поток данных при запросе

1. **HTTP запрос** поступает в `Controller` (`Presentation Layer`)
2. **Controller** валидирует данные и преобразует их в DTO
3. **Controller** вызывает метод `Service` (`Application Layer`)
4. **Service** применяет бизнес-логику и правила валидации
5. **Service** вызывает `Repository` (`Infrastructure Layer`)
6. **Repository** выполняет операцию с БД через `DbContext`
7. **БД** возвращает данные
8. Данные проходят обратно через слои: Repository → Service → DTO → HTTP Response

## Настройка строки подключения к PostgreSQL

1. Создайте файл `appsettings.json` (если его нет) в проекте `Ya.Events.WebApi` или добавьте секцию в существующий файл:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventify;Username=postgres;Password=your_password"
  }
}
```

2. Замените значения на актуальные:
   - `Host` — адрес сервера PostgreSQL (по умолчанию `localhost`)
   - `Port` — порт PostgreSQL (по умолчанию `5432`)
   - `Database` — имя базы данных (например, `eventify`)
   - `Username` — имя пользователя PostgreSQL (по умолчанию `postgres`)
   - `Password` — пароль пользователя PostgreSQL

3. Для среды разработки можно использовать файл `appsettings.Development.json`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventify_dev;Username=postgres;Password=dev_password"
  }
}
```

## Управление схемой БД через миграции EF Core

Схема базы данных управляется с помощью **миграций EF Core**. Это позволяет контролировать изменения схемы версиями и применять их последовательно.

### Установка инструментов EF Core CLI

Сначала установите инструменты EF Core CLI (если ещё не установлены):

```bash
dotnet tool install --global dotnet-ef
```

### Применение миграций

Для применения миграций к базе данных PostgreSQL:

```bash
cd src/Ya.Events.WebApi

# Примените все Pending миграции
dotnet ef database update
```

### Создание новых миграций

При изменении моделей (Event, Booking) создайте новую миграцию:

```bash
cd src/Ya.Events.WebApi

# Создайте миграцию с описательным именем
dotnet ef migrations add AddFieldNameValidation
```

### Откат миграций

Для отката на одну миграцию назад:

```bash
cd src/Ya.Events.WebApi
dotnet ef database update --target PreviousMigrationName
```

Для отката до начала (удаление всех таблиц):

```bash
dotnet ef database drop --force
```

## Использование InMemory-провайдера в юнит-тестах

Для **юнит-тестов** используется **InMemory-провайдер EF Core**, что позволяет:

- Запускать тесты без установки PostgreSQL
- Быстро изолировать тесты друг от друга
- Избегать накладных расходов на работу с реальной БД

Пример настройки контекста в юнит-тестах:

```csharp
var options = new DbContextOptionsBuilder<AppDbContext>()
    .UseInMemoryDatabase(databaseName: $"TestDb_{Guid.NewGuid()}")
    .Options;

using var context = new AppDbContext(options);
```

Каждый тест создаёт отдельную базу данных в памяти, которая удаляется после завершения теста.

## Интеграционные тесты

Для **интеграционных тестов** используется **Testcontainers.PostgreSql** — библиотека для создания изолированных контейнеров PostgreSQL на лету.

### Требования для запуска интеграционных тестов

- Установленный и запущенный **Docker** (Docker Desktop, WSL2)
- Docker-образ PostgreSQL 16+ будет автоматически скачан Testcontainers

### Как работает Testcontainers.PostgreSql

Testcontainers автоматически:
1. Запускает контейнер PostgreSQL с нужной версией образа
2. Настраивает строку подключения к контейнеру
3. Создаёт временную базу данных для каждого теста
4. Очищает контейнер после завершения теста

Пример использования в интеграционных тестах:

```csharp
public class IntegrationTestFixture : IAsyncLifetime
{
    public PostgreSqlContainer PostgreSqlContainer { get; } = 
        new PostgreSqlBuilder().Build();

    public async Task InitializeAsync() => await PostgreSqlContainer.StartAsync();
    public async Task DisposeAsync() => await PostgreSqlContainer.DisposeAsync();
}
```

### Запуск интеграционных тестов

1. Убедитесь, что Docker запущен:

```bash
docker ps
```

2. Запустите тесты:


Testcontainers автоматически:

- Очистит контейнер после завершения

## Краткая документация API

Все эндпоинты по базовому пути `/events` (кроме получения бронирования).

### Модель Event

```json
{
  "id": "guid",
  "title": "string",
  "description": "string | null",
  "startAt": "2025-06-01",
  "endAt": "2025-06-02",
  "totalSeats": 100,
  "availableSeats": 100
}
```

**Поля:**
- `id` — уникальный идентификатор события.
- `title` — название события.
- `description` — описание события.
- `startAt` — дата начала события.
- `endAt` — дата окончания события.
- `totalSeats` – общее количество мест на событии (обязательное, положительное целое).
- `availableSeats` – количество ещё доступных для бронирования мест. При создании события равно `totalSeats`. Уменьшается на 1 при каждой успешно созданной брони, увеличивается на 1 при возврате места (отклонении брони).

**Валидация:**
- `title` обязательно.
- `endAt` позже `startAt`.
- `totalSeats` ≥ 1.

### Эндпоинты

| Метод | Путь                | Описание                                | Основные ответы                      |
|-------|---------------------|-----------------------------------------|--------------------------------------|
| GET   | `/events`           | Получить все события (с фильтрацией)    | 200: Список событий                  |
| GET   | `/events/{id}`      | Получить событие по `id` (GUID)         | 200: Событие, 404: Not Found         |
| POST  | `/events`           | Создать новое событие                   | 201: Created + заголовок Location    |
| PUT   | `/events/{id}`      | Обновить событие (полный объект)        | 204: No Content, 404: Not Found      |
| DELETE| `/events/{id}`      | Удалить событие по `id` (GUID)          | 204: No Content, 404: Not Found      |
| POST  | `/events/{id}/book` | Забронировать событие                   | 202: Accepted + тело бронирования    |
| GET   | `/bookings/{id}`    | Получить информацию о бронировании      | 200: Бронирование, 404: Not Found    |

**Важно:** эндпоинт `POST /events/{id}/book` теперь может возвращать `409 Conflict` при отсутствии свободных мест (см. раздел «Примитивы синхронизации»).

### Фильтрация и пагинация для GET /events

Для `GET /events` поддерживаются параметры запроса вида:
`/events?title=Конференция&from=2025-06-01&to=2025-06-30&pageSize=10&page=2`

#### Параметры фильтрации

| Параметр   | Тип        | Описание                                                                                                  |
|------------|------------|-----------------------------------------------------------------------------------------------------------|
| `title`    | `string`   | Частичный поиск по названию события (без учёта регистра). Если не задан — фильтр не применяется.          |
| `from`     | `datetime` | Возвращает только события, у которых `startAt` ≥ указанной даты‑времени. Если не задан — нет ограничения. |
| `to`       | `datetime` | Возвращает только события, у которых `endAt` ≤ указанной даты‑времени. Если не задан — нет ограничения.   |

#### Параметры пагинации

| Параметр   | Тип    | Описание                                                                                                      |
|------------|--------|---------------------------------------------------------------------------------------------------------------|
| `pageSize` | `int`  | Количество событий на одной странице (по умолчанию 10). Если не задан — используется значение по умолчанию.   |
| `page`     | `int`  | Номер страницы (начиная с 1). Если не задан — возвращается первая страница.                                   |

### Примеры запросов GET /events

- Все события с названием, содержащим «Конференция»:
  `/events?title=Конференция`

- События в июне 2025 года:
  `/events?from=2025-06-01&to=2025-06-30`

- Пагинация: 10 событий, вторая страница:
  `/events?pageSize=10&page=2`

- Смешанный запрос:
  `/events?title=Доклад&from=2025-06-01&page=1`

При некорректных значениях (неверный формат даты, `from` позже `to`, отрицательные/нулевые числа в `pageSize`/`page`) API возвращает `400 Bad Request` с описанием ошибки.

### Пример POST‑запроса

```json
{
  "title": "Конференция",
  "description": "Описание (необязательно)",
  "startAt": "2025-06-01T10:00:00Z",
  "endAt": "2025-06-02T10:00:00Z",
  "totalSeats": 100
}
```

### Бронирование событий

#### Модель Booking

```json
{
  "id": "guid",
  "eventId": "guid",
  "status": "Pending",
  "createdAt": "2025-04-08T10:00:00Z",
  "processedAt": "2025-04-08T10:00:00Z | null"
}
```

**Поля:**
- `id` – уникальный идентификатор бронирования.
- `eventId` – идентификатор события, на которое бронируется место.
- `status` – текущий статус бронирования (см. ниже).
- `createdAt` – дата и время создания брони.
- `processedAt` – дата и время обработки брони (опционально).

### Статусы бронирования

| Статус     | Описание                            |
|------------|-------------------------------------|
| `Pending`  | Бронь создана, ожидает обработки.   |
| `Confirmed`| Бронь подтверждена.                 |
| `Rejected` | Бронь отклонена.                    |

### Фоновая обработка бронирований

- После создания бронирования (статус `Pending`) запускается фоновый сервис, который через заданный интервал (3 секунды) подтверждает бронирование, меняя его статус на `Confirmed`. Если событие было удалено до подтверждения, бронь автоматически отклоняется.
- Все изменения статусов логируются и доступны через `GET /bookings/{id}`.

### Примитивы синхронизации

Для предотвращения овербукинга (превышения доступных мест при параллельных запросах) в `BookingService` используется `SemaphoreSlim` (асинхронный семафор с начальным и максимальным счётчиком, равным 1):
- Критическая секция, защищённая семафором, включает атомарную операцию «проверка свободных мест + резервирование» (`TryReserveSeats()`). Только один поток может одновременно выполнять эту операцию для конкретного события.
- Благодаря этому при 5 свободных местах и 20 одновременных запросах ровно 5 получат успешное бронирование, а 15 – ответ `409 Conflict` с исключением `NoAvailableSeatsException`.
- Семафор не блокирует потоки, а использует асинхронное ожидание (`WaitAsync`), что важно для масштабируемости веб-приложения.

### Пример сценария бронирования

1. Пользователь находит событие через `GET /events`.
2. Отправляет `POST /events/{eventId}/book`.
3. API возвращает `202 Accepted` и бронирование со статусом `Pending`.
4. Фоновый сервис через 3 секунды подтверждает бронирование – статус становится `Confirmed`.
5. Пользователь может в любой момент проверить статус через `GET /bookings/{id}`.

### Пример сценария с овербукингом

1. Создано событие с `totalSeats = 5`.
2. Десять пользователей одновременно отправляют `POST /events/{eventId}/book`.
3. API возвращает первым пяти запросам статус `202 Accepted` и создаёт брони со статусом `Pending`.
4. Остальные пять запросов получают `409 Conflict` с сообщением `"No available seats for this event"`.
5. Фоновый сервис параллельно подтверждает пять созданных броней, статус каждой меняется на `Confirmed`.

### Формат ответов об ошибках

При ошибках валидации или бизнес‑логики возвращается `400 Bad Request` с JSON следующего вида:

```json
{
  "status": 404,
  "detail": "Событие с идентификатором '9e1514cf-90f7-46d6-9e30-8df604d59f58' не найдено."
}
```

## Технологии

- ASP.NET Core Web API
- Swagger/OpenAPI (Swashbuckle)
- Фоновые службы (IHostedService / BackgroundService)
- Entity Framework Core (PostgreSQL + InMemory для юнит-тестов)
- Миграции EF Core (для управления схемой БД)
- Testcontainers.PostgreSql (для интеграционных тестов)
